## 文档职责

本计划解决 issue #496：对本地路径的大型仓库（实测 3,200 提交线性历史）执行 `libra clone <local-path>` 时，卡在 “Fetching objects” 阶段，CPU 0%，全部线程等待（2026-09-15 在 libra 0.22.31 复现，于 `issues/486.md` 作为 ER-AB-02 的例外另行报告）。目标是消除本地路径 clone 的挂起，使其以合理时间完成，并能对 `status --short --branch` 等后续命令正常工作。

本文只规划任务，不宣称实现完成。落地时每个任务都必须先刷新源码锚点，再按任务卡验收。

### 适用范围

- `libra clone <local-path>`（本地路径源，非 URL）的打包/拉取路径，尤其是大仓库（数千提交）下的性能与并发行为。
- “Fetching objects” 进度阶段：对象编码/传输/接收的等待位置与线程挂起原因。
- 与既有 pack 编码器（`pack_writer::encode_pack_bytes`）的复用（#487 已复用的先例）。
- 相关同步：`COMPATIBILITY.md`、clone 文档、`../libra-backend` 网站文档、clone 性能回归测试。

### 非目标

- URL 远端（http/ssh）clone（#480）。
- 浅克隆 `--depth`、bundle 源、`--bare`/`--mirror`（由 #474 承接；本计划只处理「本地路径直接 clone」的挂起）。
- 网络层长连接/凭证（#480）。
- 存储格式变更。

### 成功定义

- `libra clone <local-path>`（本地路径、约 3,200 提交）在合理时间内完成，不再出现 “Fetching objects” 0% CPU 挂起。
- clone 后 `status --short --branch`、`log --oneline` 正常，`[ahead N]`/`[behind N]` 语义正确。
- 大仓库 clone 挂起不再复现（用 #486 的 R1 fixture 或等价 fixture 做回归守卫，带合理超时预算）。
- 任务卡各自取得 C 组发布与 D 组证据，收口门全绿后才标记完成。

## 已决议设计决策

实现时若需偏离本节，必须先修改计划并说明原因，不得在代码中静默改语义。

### ADR-CLH-01: 本地路径 clone 复用 `pack_writer::encode_pack_bytes`

- **Status:** Accepted
- **Context:** 复现证据（2026-09-28，本仓 `v0.27.2`）：`libra clone <local-git-path>` 克隆 4 000 提交线性历史死锁于 “Fetching objects”，`timeout 45s` 后仍 0% CPU、目标 `.libra/objects/pack/` 空；`libra clone <local-libra-path>` 克隆 900 提交同样死锁。根因与 #487 ADR-IG-01 相同：`src/internal/protocol/local_client.rs` 内嵌的 `encode_pack_bytes` 是修复前的旧实现——同一任务内先 `for entry in entries { entry_tx.send(..).await }` 喂满容量 1 000 的有界输入通道，再 `while let Some(chunk) = stream_rx.recv().await` 排空容量 1 000 的有界输出通道。对象数 > 1 000 时，编码器被写满的输出通道阻塞（不再消费输入），喂入循环被写满的输入通道阻塞（不再排空输出）→ 循环等待、全部线程 sleep（`/proc/<pid>/task/*/stat` 状态 `S`，`utime`≈0）。`pack_writer::encode_pack_bytes` 已用「独立 feed 任务 + 主任务排空」修复（见其 `// deadlock` 注释）。
- **Decision:** 删除 `local_client.rs` 的 `encode_pack_bytes`，`encode_entries_to_fetch_response` 改为调用 `crate::internal::pack_writer::encode_pack_bytes`（签名一致：`fn(Vec<Entry>, HashKind) -> io::Result<Vec<u8>>`），并移除不再使用的 `EntryMeta`/`MetaAttached`/`PackEncoder` 导入。本地 Git 与本地 Libra 其实例（`RepoType::GitRepo` / `RepoType::LibraRepo`）均经 `encode_entries_to_fetch_response`，故同一条修复同时覆盖两种本地源。
- **Alternatives considered:** 在 `local_client.rs` 内原地修补——保留两份实现，违反 GC-02（单一来源），拒绝；`pack_writer` 只为“磁盘写文件”服务、`local_client` 为“sideband 帧”服务——两者 `encode_pack_bytes` 本身就是同一 `PackEncoder` 同一输出，只是下游 sink 不同（帧 vs 写盘），复用字节级编码器不影响各自 sink（ADR-IG-01 同结论）。
- **Consequences:** 本地传输与 `repack`/`pack-objects`/`maintenance` 共用同一编码器，`pack_writer` 后续修复自动覆盖本地传输；本地路径 clone 不再挂起，且 `status --short --branch`/`log --oneline` 可正常使用。
- **Revisit when:** 需要流式/增量编码接口时，在 `pack_writer` 内扩展，而非复制（同 ADR-IG-01）。

## 任务卡

### Task CLH-01: 复现并定位本地路径 clone 挂起点
- 输入：#496 / #486 的复现步骤与 R1 fixture。
- 输出：挂起处的等待位置（线程栈/`lsan`/进度状态），给出根本原因定性（死锁 vs O(n²) vs 未收到远端信号）。
- 验收：写出具体代码位置与根因，形成 ADR-CLH-01。
- **状态：`done`**。复现：本地 Git 4 000 提交 / 本地 Libra 900 提交均死锁于 “Fetching objects”，`timeout 45s` 0% CPU；`/proc/<pid>/task/*/stat` 全部 `S`。根因：`local_client.rs` 旧 `encode_pack_bytes` 同一任务先喂满有界输入通道再排空有界输出通道造成的循环等待（死亡阈值 > 1 000 对象）。ADR-CLH-01 见上。

### Task CLH-02: 本地路径源走正确传输路径
- 输入：CLH-01 定位结果。
- 输出：本地路径源不再进入无限等待的远端获取路径；复用已修复的 pack 编码器。
- 验收：本地路径 clone 3,200 提交仓库能完成，不再 0% CPU 挂起。
- **状态：`done`**。删除 `local_client.rs::encode_pack_bytes`，`encode_entries_to_fetch_response` 改调 `crate::internal::pack_writer::encode_pack_bytes`，移除 `EntryMeta`/`MetaAttached`/`PackEncoder` 导入。验证：本地 Git 4 000 提交 7s 完成、本地 Libra 900 提交 1s 完成，`status --short --branch` 与 `log --oneline`（4 000 / 900 条全量）正常。
